# AGENTS.md

このファイルを、対象プロジェクトのルートへ `AGENTS.md` としてコピーして使ってください。

## Project Rules

- 憶測で作業を行わず確かな根拠に基づいて作業を実施してください。たとえば、バグが出たときに場当たり的な対応をせず、まずは調査し原因をつきとめたうえで、手戻りを最小限におさえた改善対応を行ってください。
- ブランチ名に master を使わず main を使うようにしてください。
- コミットメッセージは日本語で書いてください。
- 新たな計画を作成した際は、都度 .prompts/PLANS 配下に新規で保存してください。
  - 計画を立てた後は、その計画をノンバイアスで読み直し、懸念点を `.prompts/DISCUSSIONS/` 配下に md ファイルとして洗い出して、私に回答を求めてください。私の回答を得てから承認フローに進んでください。
    - 懸念点ごとに、推奨案を含む複数案を提示してください。推奨案にはその旨を明記してください。
  - 計画を立てた後は私に承認を促してください。私が承認してから計画を実行するようにしてください。
  - プランファイルは、ゼロ文脈で読んでそのまま作業開始できる自己完結した内容にしてください。
    - 対象ファイルパス、URL、コマンド例など、作業に必要な具体的情報を記載してください。
    - 重複した記述は排除し、必要十分な情報量に留めてください。
  - CLI 操作で完結できるタスクは Codex 側で自律的に完結するプランを提示してください。人間の介入は意思決定、承認、外部認証など Codex では代替できない操作に限定してください。
  - 多段階の計画は、結果次第で以降の前提が変わる初手ステップ (情報取得や可否判定など) に絞って提示してください。続きはその結果を確認してから別の計画として立ててください。早い段階で前提を確証し、無駄な計画立案や実装を避けるためです。
- .git/info/exclude に書かれた AGENTS.md, .prompts などの除外設定は意図的なものです。作業時はこれを尊重してください。
  - .gitignore の内容が常に正しいか検討するようにしてください。 .git/info/exclude に含まれているものを二重に除外する必要はありません。
- 複数コマンドが必要な場合は、個別のコマンド実行に分けてください。
  - `&&` や `|` でコマンドを連結しないでください。
    - 悪い例: `cd app && npm test`
    - 良い例: `cd app` → `npm test`
  - パイプの代わりに一時ファイル (`.tmp` 配下) へリダイレクトし、結果はファイル読み取りで確認してください。
    - 悪い例: `npm test 2>&1 | tail -60`
    - 良い例: `npm test 2>&1 > .tmp/test.txt` → `.tmp/test.txt` を読む
- git -C コマンドを使わず、作業ディレクトリを指定する方法で対応してください。
- .prompts/INSPECTIONS 配下の .sarif.json の分析のために、まず .prompts/INSPECTIONS/extract.py を作成し、必要な部分だけを抽出するようにしてください。
- 調査内容、実行ログ、レポートは `docs/reports` や `docs/logs` に蓄積してください。context compacting で情報が失われても、ファイルから再取得できる状態を維持するためです。
  - `docs/INDEX.md` を作成・更新し、何がどこに書かれているかを一覧化してください。
- README にはプロジェクトの目的、背景情報、内容物、使い方などを網羅的に記載し、初見の人が全貌を把握し滞りなくタスクを進められるようにしてください。 README の末尾にはバージョンごとの更新情報を記載してください。

## Beads による進捗管理

- 複数セッションへまたがる作業、依存関係、ブロッカー、後続課題は Beads へ登録してください。回答だけの依頼や、数分から数十分で完了する単発作業は登録しないでください。
- `.prompts/PLANS` は設計と承認の記録です。Beads は実行中の状態、依存関係、ブロッカー、次の作業の正本です。Codex のセッション内プランは、そのセッションで使うチェックリストとして扱ってください。
- 作業開始時は `bd ready` で着手可能な課題を確認し、`bd update <id> --claim` で担当を記録してください。事実が判明した時点は `bd note <id> <内容>`、完了時は検証結果を含む `bd close <id> --reason <理由>` を使ってください。
- 継続的に必要なリポジトリ固有の決定は `bd remember` に記録してください。
- Beads データベースがなく、`.beads-optout` もない場合は、次のコマンドで個人用の進捗管理を初期化してください。

```powershell
bd init --stealth --skip-agents --non-interactive --init-if-missing
```

- `.beads-optout` があるリポジトリでは Beads を初期化または使用しないでください。`.beads/` は進捗データを含むため、取り消し処理や一時ファイル削除の対象にしてはいけません。
- Beads 公式の Codex 統合が有効な場合、`bd prime` のセッション注入と圧縮対応を独自フックで重複実装しないでください。
- `bd dolt push` は外部への書き込みです。利用者から明示的に指示された場合だけ実行してください。
## Working Principles

### 事実と根拠を検証する

- ユーザーの発言、実験結果、測定値、ツールの表示を鵜呑みにしないでください。小さすぎる値、大きすぎる値、想定と食い違う結果は、対照実験や別経路の確認で裏を取ってください。
- 仕様や挙動を憶測で語らないでください。未知のコマンドやフラグは実行前に挙動を確認し、主張は公式ドキュメントで裏付けてください。
- 調査結果を安易に「確定」「決定的」と断定しないでください。その証跡から分かること、否定できること、まだ確認できていない範囲を分けて述べてください。
- グローバルの `AGENTS.md`、過去の会話、メモリに残る環境情報を現在の実態として扱わないでください。ファイル、関数、フラグに言及する場合は、現在も存在するか確認してから利用してください。
- 課金やコストに言及する前に、公式単価と実測量を調べて月額換算の桁を示してください。月額が無視できる額なら、その点も判断材料として伝えてください。

### エラーと証拠なしを同じ 0 件にしない

- 調査結果を報告するとき、エラー、証拠なし、判定不能を同じ 0 件として扱わないでください。コマンドが失敗した結果の 0 件と、調べた結果として存在しない 0 件は異なる情報です。
- 結果は最低でも、肯定証拠あり、調査して証拠なし、調査不能、内容は見つかったが出所を証明できない、の 4 状態に分けてください。
- 判定に使う経路では、標準エラーを破棄しないでください。エラーを結果の一部として記録し、失敗を 0 件に変換しないでください。
- JSON などの構造化データは、生のテキスト検索だけで判定しないでください。キーと構造を指定できる `jq` や JSON 解析機能を使用してください。

### 調査を先行させる

- ユーザーに質問する前に、答えられるものは自分で調べてください。git 履歴、公式ドキュメント、既存リポジトリ、`docs/reports`、`docs/logs`、過去の引き継ぎ資料などを先に確認し、質問は調査後に残った情報差分だけに絞ってください。
- deploy、login、新規ツールの呼び出しなど、初めてに見える操作の前に、過去に同じ操作を実施していないか記録を検索してください。
- 実装の変更計画や質問リストを作る前に、対象ファイルを通読してください。検索結果だけで判断すると、既存機能や前提を見落とす可能性があります。
- 大きなストレージやリソース群 (S3、既存 Terraform、既存設計など) を扱うときは、最上位から網羅的に一覧化してから着手してください。
- 大量のファイル読み込みや、ログ・原因の丁寧な分析が必要な作業は、サブエージェントに委譲してください。独立した調査や後続手順の準備は、共有リソースを占有する作業と並行して進めてください。

### スコープと判断を適切に分担する

- 依頼の文面にない要素を計画へ追加しないでください。自分で判断できることを質問として返すことも避けてください。
- 自分で調べれば分かることと、相手にしか分からないことを切り分け、後者だけを確認してください。
- 技術的な制約 (閾値、桁数、上限など) を設計に持ち込むときは、それが要件なのか思い込みなのかを確認してください。制約に合わせて要件変更を求める前に、制約を緩められないか検討してください。
- 指示に違和感がある場合や複数の解釈が成り立つ場合は、修正に着手する前に確認してください。
- 「完了」「動作確認済み」と報告する前に、合意したスコープと突き合わせてください。起動確認だけでなく、本来の成果が正常に得られるところまで確認してください。

### 報告・相談・依頼を的確に伝える

- 報告と相談を区別してください。報告は判断を求めない情報伝達、相談は相手の判断が必要な行為です。
- 報告は「これまで → 現在 → これから」の順で書き、相手が現在地を把握できるようにしてください。
- 相談では判断を丸投げしないでください。判断材料と推奨案を添えて、最終判断を求めてください。
- 相手の認知負荷を下げることを優先してください。
- 冒頭には相手が最も知りたい結論を書いてください。詳細データは必要に応じて別ファイルにまとめ、参照先を示してください。
- 相手が今判断すべきことを明示してください。判断が不要な場合は、その旨を伝えてください。
- 作業に着手する前に、進める方向を一言伝えてください。
- 悪い報告ほど早く共有してください。自分の体裁より、早期に軌道修正できることを優先してください。
- 質問は、回答によって相手のアクションが変わるかを確認してください。変わらない質問は削除し、本質的な問いに絞ってください。
- 相手からの質問や指示に答えるときは、要約や引き継ぎだけでなく、確認できる場合は原文を直接確認してください。

### 外部への書き込みと公開を慎重に扱う

- チケット管理ツールやチャットなど、相手から見える場所への書き込み操作 (投稿、コメント、課題の作成や編集など) は、原則として Codex が直接実行せず、文案を作ってユーザーに委ねてください。参照操作は行ってかまいません。
- リポジトリへの push や成果物の共有の前に、ユーザーのレビューを挟んでください。commit 直後に自己判断で push しないでください。
- 顧客や第三者に関するネガティブな情報は、git 管理下のファイルに含めないでください。必要な場合は、除外領域 (`.prompts/` など) に留めてください。

### 破壊的操作には保険をかける

- `terraform destroy`、`force_destroy=true`、一括削除を実行する前に、削除対象を一覧で確認し、復旧が困難なデータはバックアップしてください。
- 他者のクラウドアカウントで作業するときは、未使用のまま課金が続くリソース (Public IPv4、EIP、NAT、起動中インスタンスなど) を残置しないでください。

### 日本語出力に不自然な半角スペースを入れない

- Codex のあらゆる出力 (ユーザーへの応答、新規作成する markdown、コミットメッセージ、UI テキスト、チャットやチケットへの投稿文案など) で、日本語として不自然な半角スペースを入れないでください。特に次の箇所を分断してはいけません。
  - 助詞の前後: 「担当者 が」ではなく「担当者が」、「サイドバー を」ではなく「サイドバーを」
  - 動詞の活用: 「なって おります」ではなく「なっております」、「実施 しました」ではなく「実施しました」
  - 謙譲語・丁寧語の接頭辞: 「ご 確認」ではなく「ご確認」、「お 世話」ではなく「お世話」
  - 複合名詞: 「疎通 確認」ではなく「疎通確認」、「更新 内容」ではなく「更新内容」
- Documentation セクションの「半角の文字列と全角の文字列の間にスペースを挿入する」というルールは、半角英数字と全角文字の境界にだけ適用してください。日本語の語を機械的に分断してはいけません。
- ユーザーへの応答、UI に表示する文字列、チャット、チケット、メール向けの文案では、境界スペースより自然な日本語を優先してください。「7 つ」ではなく「7つ」、「API で」ではなく「APIで」、「( 任意 )」ではなく「(任意)」のように調整してください。
- 半角英数字どうし (「3ds Max 2024」など) や、数値と単位 (「5 分」「10 件」など) のスペースは維持してかまいません。
- 書き終えたら、助詞、活用語尾、接頭辞の直前に不自然な半角スペースがないか確認してください。

### セッションとツール出力を確認可能にする

- ユーザーへの応答は日本語で書いてください。コード、コマンド、識別子、エラーメッセージの引用はそのままでかまいません。
- シェルスクリプトの標準出力と標準エラーは `.logs/<script-name>-<timestamp>.log` に記録してください。長時間実行が失敗したときに、後から確認できるようにするためです。
- ユーザーに実行してもらう複数行のコマンドは markdown ファイルに出力し、ファイルパスを伝えてください。チャットからのコピーで改行やタブが崩れることを防ぐためです。

### 環境とツールを使い分ける

- プロジェクト固有の依存は、そのプロジェクト内 (Python なら `.venv`、Node.js なら devDependencies や `npx` など) に閉じ込め、グローバル環境を変更しないでください。
- 他のプロジェクトでも再利用できる汎用ツール (ヘッドレスブラウザ、HTTP クライアント、フォーマッタなど) は、グローバルにインストールしてかまいません。実行前に用途と再利用可能性を伝え、大きなバイナリはインストール先も伝えてください。
- その場限りの認証情報は一時ファイルへ保存しないでください。プロセスの環境変数などを使用し、一時的な env ファイルを残さないでください。

## Testing

- 開発は原則として TDD (テスト駆動開発) で行ってください。TDD が適さないと判断した場合は、作業を進める前に人間に相談してください。
- test に失敗したときは、場当たり的に test を修正せず、まずは実装の誤りを疑ってください。
- coverage を 100% に近づけてください。
- 外部依存 (fetch や外部 API) を mock したユニットテストでは、CORS、認証、遅延といった実環境の制約を検出できないことを認識してください。mock は引数と戻り値の伝搬しか検証しないため、pass した後に実環境でも確認してください。

## Documentation

- 日本語で書いてください。
- 図は mermaid で書いてください。
- 技術文書としてふさわしいフォーマル寄りの文体で文章を執筆してください。
- 専門用語が出現したときは適宜その意味を補完するよう努めてください。
- 半角の文字列と、全角の文字列の間にはスペースを挿入してください。
  - ただし句読点の直後であればスペース挿入は省略して良いものとします。検索性を高めるためです。
  - このスペースは半角英数字と全角文字の境界にだけ入れてください。全角文字どうしの間、特に助詞の前後、動詞の活用、謙譲語・丁寧語の接頭辞を分断するスペースは挿入しないでください。
  - 境界スペースは、検索性を優先する `docs/` 配下の技術文書に適用してください。ユーザーへの応答、UI に表示する文字列、チャットやチケットへの投稿文案では、自然な日本語を優先してください。
- 全角かっこ、全角コロンは決して使用しないでください。
  - 半角かっこを使用する際、前かっこでは `[space](` の形で、後ろかっこでは `)[space]` の形でスペースを挿入してください。半角コロンを使用する際は `:[space]` の形でスペースを挿入してください。

```
悪い例: これをARGといいます。
良い例1: これを ARG といいます。
良い例2: これを、ARG といいます。
```

```
悪い例1: 代替現実ゲーム（ARG）は、
悪い例2: 代替現実ゲーム ( ARG ) は、
良い例: 代替現実ゲーム (ARG) は、
```

```
悪い例1: ARG：代替現実ゲーム
悪い例2: ARG : 代替現実ゲーム
良い例: ARG: 代替現実ゲーム
```

- ダブルクオーテーションは日本語文章中には決して使用しないでください。
- 「ひとつひとつ」「一発逆転」のような日本語の言葉を、「 1 つ 1 つ」「1発逆転」のように算用数字で書いてはいけません。
  - 「第 1 回」「第 2 回」、「1 点のメリット」「2 点のメリット」のように、異なる数に置き換えられるものは算用数字で書いてかまいません。
  - 1,000 のように、 4 桁以上の数にはコンマを付けてください。
- 衒学的な表現はなるべく避け、平易な日本語で記載してください。
  - 「〇〇を実現します」 「〇〇を実施します」などの表現は、「〇〇できます」 「〇〇します」 という表現で書けないか常に検討してください。冗長な表現を避け端的に表現してください。

```
悪い例: 解説が行われました
```

```
良い例: 解説されました
```

- 「〇〇で、〇〇」のように並列的に並べることで冗長な表現になることを必ず避けてください。
  - 一文の長さが長くなりすぎないよう適切に区切ってください。

```
悪い例: Python はインタプリタ言語で、低速です。
```

```
良い例: Python はインタプリタ言語です。また、低速です。
```

- むやみに箇条書きを挿入すべきではありません。日本語文の途中で箇条書きが挿入されるのは日本語文章として不自然だからです。
  - 文の形で完結させるよう努め、項目の並列性がある場合のみ箇条書きを使用してください。

悪い例:
```
検証環境として
* Windows
* Next.js
を使用しました。
```

良い例1:
```
検証環境として、Windows と Next.js を使用しました。
```

良い例2:
```
検証環境は以下の通りです。
* Windows
* Next.js
```

- 助詞を適切に使用してください。特に、「以下」「次」「は」のワードについては細心の注意を払ってください。

悪い例
```
設定内容は次とします。
```

良い例
```
設定内容は次のようにします。
```

悪い例
```
get() は、ユーザーが情報を取得します。
```

良い例 (ユーザーを主語にする場合)
```
get() では、ユーザーが情報を取得します。
```

良い例 (get を主語にする場合)
